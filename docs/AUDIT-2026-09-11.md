# CLI audit — 2026-09-11

Release: `@quaivault/cli@0.6.1`, using `@quaivault/sdk@0.6.1`.

## Scope

Reviewed the command registry and SDK capability coverage, proposal and lifecycle
signing, recovery, key storage, policy enforcement, durable journals, rendering,
JSON protocol, packaging, and release gates. The existing `CAPABILITIES.md` covers
the intended one-shot and TUI workflows; no missing material workflow was found.
Low-level module integration remains available through SDK ABIs rather than a
separate owner command. The website reference needed the existing recovery module
shortcuts and the 0.6.1 security behavior documented.

## Findings fixed

| Severity | Finding | Fix |
| --- | --- | --- |
| High | RPC/signer network and external address not consistently checked | SDK 0.6.1 guards every high-level broadcast; invalid network names fail closed |
| High | Environment identity differed from the identity checked at unlock | Use the same flag/environment/profile precedence for both |
| High | Malformed policy fields silently removed limits | Strict validation of all fields, lists, types, and limits |
| High | Hourly limits recorded only after successful receipt lookup | Reserve budget durably before signing under a shared journal lock |
| High | Proposal deduplication had a submission-to-journal crash window | Reserve keyed intent before submission and block unresolved retries |
| High | Two-minute expiry could steal a live signing lock | No automatic lock reclamation; reconciliation required after crashes |
| High | Keystore resource checks bounded only scrypt N | Bound N/r/p, combined work, PBKDF2 iterations, key length, and salt |
| High | Concurrent key imports could overwrite a signing key | Atomic create-if-absent publication of encrypted files |
| Medium | Invalid scalar errors could disclose raw private keys | Generic key-validation errors without cryptographic payloads |
| Medium | Receipt timeout implied unchanged state and lost the submitted hash | `BROADCAST_UNKNOWN`, `changed: "unknown"`, hash in JSON data/error |
| Medium | Terminal target failure reported no state change | Report `changed: true` for the consumed proposal |
| Maintenance | Vulnerable development dependencies | Vitest 4.1.11 and compatible transitive patches |

## Verification

- 512 tests pass, including all four subprocess JSON tests, on Node 22.23.2 and Node 26.
- Typecheck, lint, and build pass with the packed SDK 0.6.1 candidate installed.
- SDK capability coverage has no unclassified exports or known workflow gaps.
- npm audit reports zero known vulnerabilities in the lockfile dependency tree.
- A read-only CLI mainnet vault lookup passes with an isolated config directory and no signing environment.
- SDK separately passes 251 tests, both supported quais peer versions, ABI checks,
  package import checks, and read-only mainnet verification.

No funded on-chain write was performed. This is an application audit, not a formal
proof or an independent contract audit. A pending idempotency record is intentionally
conservative: even a failure before broadcast requires reconciliation before reuse.
Approval reservations consume budget for an hour even if the eventual call fails.
Abandoned signing or journal locks are not automatically removed.
